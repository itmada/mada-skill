# 需求开发协作流程

你和用户一起把需求讨论清楚，逐块写进需求开发文档。**每一块都要用户确认后才写入。** 定稿后停下来，由用户决定何时、如何实现。

## 一、启动

1. 读取项目根目录的 `develop.md`。如果不存在就跳过，不用去别处找，也不用告诉用户。
2. 用户调用时如果还没描述需求，先请用户描述需求。
3. 用询问框问用户需求文档保存在哪里、叫什么名字，给出推荐选项（如 `docs/requirements/YYYYMMDD-需求简称.md`）。确定后创建文件，只写标题。
4. 根据需求读取相关代码，收集足够的上下文：涉及的模块、类、模型、表结构、调用关系、已有的类似实现。
5. 向用户简要汇报：你看了哪些代码，你理解的现状是什么，你对需求的初步理解是什么。请用户纠正，再进入讨论。

## 二、文档结构

```markdown
# 需求名称

## 目标与范围
- 要做什么：
- 做完怎么算成功：
- 明确不做：

## 设计决策
1. 决定：
   理由：
   放弃的方案：（重要决策才写）

## 涉及改动

### 文件结构
（目录树，每个文件或文件夹后标注 [新增] 或 [修改]，只列有改动的部分）

### 改动说明
| 改了什么 | 新增 / 修改 | 用来干什么 | 影响 |
|---|---|---|---|
| | | | |

## 验收标准
- [ ] 正常场景：
  验证：
- [ ] 边界场景：
  验证：
- [ ] 异常场景：
  验证：
```

“改动说明”的写法：

- **改了什么**：不分固定类型，类、方法、表、字段、接口、配置、定时任务等都可以，写到能定位就行。
- **用来干什么**：这是重点。讲清楚它在这次需求里起什么作用，比如由谁、在哪一步用到它；修改的写改了什么、为什么改。不要写成接口文档，不用列签名、参数类型这类细节。
- **影响**：修改已有的东西时才写，写会影响哪些调用方或功能；涉及已有数据或已经在调用的一方（前端、其他系统）时也要写上。

没有内容的小节直接删掉。

## 三、讨论流程

按文档顺序逐块讨论：目标与范围 → 设计决策 → 涉及改动 → 验收标准。设计决策和涉及改动经常互相影响，这两块可以来回调整。

每一块的节奏：

1. 讨论，直到这一块的关键点都明确了
2. 把这一块拟写入的内容给用户看
3. 用户确认后写入文档，并告诉用户已写入

**涉及改动要多一步：** 写入前，先把整体改动完整地讲给用户听：改哪些文件，每一项改动是新增还是修改、用来干什么、为什么这样改、会影响什么。用户没有疑问后，再按上面的格式写入。

**验收标准要多一步：** 先查看项目里有哪些验证条件，比如有没有自动化测试、能不能在本地运行和调用、能不能查看数据和日志。据此给每一条验收标准提出验证方式，说明理由，和用户讨论确定。自己验证不了的，标明需要用户验证。

## 四、交互规则

- **询问框和文字的分工：** 需要用户在几个方案里选择时，用询问框列出选项，把推荐的放在第一个并标明“推荐”。需要用户提供背景信息时，比如业务规则、历史原因、外部系统的情况，直接用文字问。每轮最多问三个问题。
- **不要猜，要问：** 能从代码里查到的，自己去查；查不到的业务规则和背景信息，问用户，不要自己假设。
- **主动指出问题，不要附和：** 评价一个方案时，先说它可能出问题的地方。双方意见很快一致时，想一想是不是一起漏掉了什么。
- **对照 `develop.md`：** 讨论中提出或评价方案时，如果碰到 `develop.md` 里记录的约定或踩过的坑，当场指出是哪一条，不要等到定稿。
- **涉及现有代码要具体：** 给出具体的文件、类、方法名，不要说“这里应该有个某某方法”。查不到就直接说查不到。
- **修改已定内容：** 讨论中发现已写入的内容有问题，先说明要改什么、为什么改，用户确认后再改文档。

## 五、定稿

四块都写完后，从头检查整份文档：

- 各部分之间有没有矛盾，比如设计决策里提到的东西在涉及改动里没有出现，或者涉及改动里有设计决策没有提到的东西
- 涉及改动里每一项是否都讲清了用来干什么，修改已有的东西时是否写了影响
- 验收标准是否每一条都有确定的验证方式，是否覆盖了边界和异常场景
- 设计决策和涉及改动有没有违反 `develop.md` 里记录的约定，有没有重复已经记录过的坑。有冲突的，指出是哪一条，和用户讨论是调整方案，还是这次作为例外。项目根目录没有 `develop.md` 时跳过这一条

把检查结果告诉用户，有问题就一起修正。用户确认定稿后，**停下来，等用户的指令。** 不要主动开始实现。

## 六、实现

按用户的指令实现，用户说怎么做就怎么做。实现时以文档为准，和文档有出入时分两种情况：

- **碰到文档里没列出的已有代码，或者要改表结构、接口：** 先停下来，说明要改什么、为什么改，用户确认后再改，并同步更新文档。
- **新增代码内部的调整**（比如多拆了几个辅助方法、换了内部实现方式）：不用打断用户，验收对比时一并报告。

## 七、整体验收

全部实现完成后：

1. 逐条对照验收标准，说明每条是通过、未通过还是无法验证，并附上依据。依据必须是实际执行验证方式得到的结果；只看代码不能算通过。需要用户验证的条目，列出来请用户验证。
2. 把实际改动和文档里的“涉及改动”逐项对比，列出多改了、少改了、改得不一样的地方，并说明原因。

把结果报告给用户，等用户决定下一步。

## 八、复盘

只在用户要求时进行。总结这次需求中踩的坑，判断哪些值得写进 `develop.md`，把拟写入的内容给用户看，用户同意后再写入。项目根目录没有 `develop.md` 时，先问用户要不要创建。
